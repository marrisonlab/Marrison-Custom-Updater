1. Plugin Architecture

The plugin is structured as a singleton class that uses Traits to organize functionality. The main MCU_Custom_Updater class extends native WordPress functionality to manage updates from custom repositories. The traits used are: AdminUITrait for the admin interface, UpdateOperationsTrait for update operations, SchedulingTrait for cron job management, and BackupTrait for the backup and restore system.

2. Repository Configuration

The plugin connects to external repositories via index.php files that return a JSON array. For plugins, the file must contain an array of objects with the following required fields: slug (unique plugin identifier), version (current version), name (plugin name), and download_url (URL of the ZIP file to download). Example JSON structure: [{"slug":"my-plugin","version":"1.0.0","name":"My Plugin","download_url":"https://example.com/repo/my-plugin.zip"}]. The repository URL is saved in WordPress options as marrison_repo_url for plugins and marrison_themes_repo_url for themes.

3. Cache System

The plugin uses WordPress transients to store update information and reduce HTTP calls. The marrison_available_updates_v2 transient stores the list of available plugins from the private repository with a duration of 6 hours (21600 seconds). The marrison_available_theme_updates transient does the same for themes. The marrison_updater_github_version transient stores the plugin version from the official repository. Failure transients (marrison_updates_fetch_failed, marrison_theme_updates_fetch_failed, marrison_github_fetch_failed) are used to avoid repeated calls when the repository is unreachable.

4. WordPress Hooks and Filters

The plugin integrates with the native update system via the site_transient_update_plugins and site_transient_update_themes filters with priority 999. These filters are hooked via admin_init to avoid running checks on the frontend. The plugins_api filter with priority 20 is used to provide plugin information when the user clicks "View details" in the plugin list. The plugin also uses the upgrader_process_complete hook to update the last update timestamp and trigger Elementor DB update if necessary.

5. Update Operations

The perform_update method in UpdateOperationsTrait manages the update process. It uses WP_Filesystem for file operations. The process implements an atomic copy-then-swap system: first copies new files to a temporary directory, then renames the old directory to backup and the new directory to the final position. This avoids leaving the plugin in an inconsistent state if the copy fails. After success, the backup directory is deleted. The method handles both folder-based plugins and single-file plugins.

6. Backup System

Backups are created automatically before every update operation. Files are compressed in ZIP format and saved in the /wp-content/marrison-backups/ directory. The ZIP filename follows the format {slug}-{version}-{timestamp}.zip. The plugin includes an automatic cleanup function that removes backups of uninstalled plugins when accessing the Backup section. Restore occurs by extracting the ZIP to the plugin position and, if necessary, reactivating the plugin via activate_plugin with the silent=true parameter.

7. Exclusion Management

Plugins can be excluded from automatic updates via the marrison_excluded_plugins option, which stores an array of excluded plugin slugs. The exclusion status is checked before every update operation, both manual and scheduled. Excluded plugins are displayed with a badge in the dashboard and can be re-enabled for updates by removing them from the exclusion list.

8. Scheduling and Cron

The plugin uses WP-Cron to execute automatic updates. The cron job is registered with the configured frequency (daily, weekly, monthly, semi-annual). The run_scheduled_updates method in SchedulingTrait performs update checks, installs new versions, creates backups, and sends an email report. The email includes the list of updated plugins with versions, any errors, skipped plugins with reasons, and the status of Elementor database update if present.

9. AJAX Handlers

The plugin registers several AJAX handlers for admin-side operations: update_plugin_ajax to update a single plugin, bulk_update_ajax for multiple updates, restore_backup_ajax to restore a backup, exclude_plugin_ajax to exclude a plugin, and force_clear_cache_ajax to clear cache and force a new check. All handlers verify user permissions via current_user_can and use check_ajax_referer for CSRF security.

10. Self-Update

The plugin can update itself automatically by checking releases from the official repository. The check_self_update method verifies the available version against the installed version. If a new version is available, the plugin injects update information into the update_plugins transient. Self-update is managed via perform_self_update which uses special logic to rename the plugin folder during update, since the running plugin cannot be directly overwritten.

11. Notification Badge

The notification badge in the admin menu is managed via the marrison_available_updates_count option. This value is calculated by the check_for_available_updates method which sums the number of plugins and themes with available updates. The method runs on admin_init to ensure the badge always reflects the real state, leveraging transient cache to avoid repeated HTTP calls.

12. Server Requirements

The plugin requires WordPress 6.0 or higher and PHP 7.4 or higher. The PHP ZIP extension is required for backup creation. The /wp-content/plugins/ and /wp-content/themes/ directories must be writable. For proper cron job functionality, WP-Cron must be enabled (default on WordPress). HTTP timeout is configured to 15 seconds for repository requests and 10 seconds for GitHub API requests.

13. Error Handling

The plugin implements an error handling system that logs failed operations via error_log. In case of failure during an update, the backup is maintained to allow restore. Failure transients are set when the repository is unreachable to avoid repeated calls. Errors are included in email reports for scheduled updates. AJAX handlers return JSON responses with error details to allow display in the user interface.
